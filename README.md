# AI-Assisted ASC 606 Contract Review: sample workpaper

A complete, fictional sample workpaper for a human-in-the-loop generative AI workflow in revenue recognition: workflow design, a 16-risk register mapped to NIST AI 600-1, 14 controls, 14 test cases, a 25-contract test sample, 4 findings, remediation and the evidence pack an auditor would ask for.

> Fictional data throughout. This is a training and portfolio sample: not an audit opinion, not legal advice, and not a NIST-endorsed method.

## Problem

Companies are putting generative AI between a contract and a revenue conclusion faster than the control framework for that step is being written. A revenue team needs to answer three evidence questions: can every extracted term be traced to a cited clause, did a qualified reviewer actually reconcile it, and can a wrong conclusion reach the general ledger?

This workpaper works one full control cycle around those questions for a fictional private SaaS company preparing for an IPO. It is a workpaper rather than an essay: front sheet and index, tickmarks, source records, reviewer notes, open items and a subsequent-events log.

## Method

- 16-risk register with inherent and residual ratings, mapped to the NIST AI 600-1 Generative AI Profile.
- 14 controls across input, extraction, human review, posting and monitoring layers, with owners, frequency and evidence references.
- 14 test cases with seeded model failures, including a prompt-injection case in a contract exhibit, personal-data masking before inference and in logs, and low-confidence routing on a poor-quality scan.
- A 25-contract sample from a 240-contract population: model extraction is reconciled field by field to the cited clause by a named reviewer, with a second-level reviewer on high-value, non-standard, low-confidence and new-SKU contracts.
- One data module (`build/wpdata.py`) generates the workpaper tables and the workbook, so the two cannot drift apart.
- An evidence pack for one contract with a SHA-256 manifest, plus the 16-artifact evidence standard an auditor would request.

## Result

Headline numbers are generated from the same data as the tables. The interesting result is not the accuracy figure; it is that the review layer, not the model, is where the corrections came from.

| Metric | Value | Where to check it |
|---|---|---|
| Contracts tested | 25 of 240 | `workpaper/AI-ASC606-Contract-Review-Workpaper.md` |
| Field-level extraction accuracy | 94.4% (236 of 250 checks) | `AI-ASC606-Test-Workbook.xlsx (Metrics)` |
| Contracts accepted with no change | 20 of 25 (80%) | `AI-ASC606-Test-Workbook.xlsx (Metrics)` |
| Conclusions changed under review | 5 of 25; independent recalculation corrected 2 more | `workpaper/AI-ASC606-Contract-Review-Workpaper.md §7` |
| Gross effect of corrections | $757,347 = 2.7% of sample value, 91.8% of performance materiality | `AI-ASC606-Test-Workbook.xlsx (Metrics)` |
| Errors that reached the general ledger | 0 | `AI-ASC606-Test-Workbook.xlsx (Metrics)` |
| Controls rated effective | 12 of 14; 3 failed or had design gaps | `AI-ASC606-Test-Workbook.xlsx (Control Matrix)` |
| Findings | 4 findings, 3 observations | `workpaper/AI-ASC606-Contract-Review-Workpaper.md §8` |
| Review time per contract | 4.2 h manual baseline to 1.6 h with the tool (62% reduction) | `AI-ASC606-Test-Workbook.xlsx (Metrics); O-03` |

The failures are documented rather than hidden: one change-control gap, one reference-data design deficiency, one reviewer sign-off gap, and one vendor logging gap that was remediated. The remediation plan and owners are in the workbook and workpaper.

## Limitations

- Fictional data throughout: the company, the tool, the customers, the people and all amounts are invented. The accounting conclusions are illustrative and would need review by a qualified accountant before use on real contracts.
- The 25-item sample is a readiness sample. Section 6.3 of the workpaper explains why it cannot support a statistically projectable misstatement estimate.
- NIST AI 600-1 is used as a voluntary risk-identification checklist. NIST does not endorse this workpaper or its control design.
- Workbook values are static, generated by the build script rather than by spreadsheet formulas.
- The PDF and workbook were checked by rendering and by reading values back, not by opening them in Excel or Acrobat.
- Rebuild requires the GenOffice CLI and headless Chrome; neither tool is vendored here.
- The control design fits one fictional company; it is not a claim that it is sufficient elsewhere.

## Rebuild

The deliverables are generated from one data module. The build needs the tools the original project used; they are not vendored here.

```bash
cd build
python3 wpdata.py                 # print the summary metrics
python3 render.py                 # Markdown + HTML
"/Applications/Google Chrome.app/Contents/MacOS/Google Chrome" --headless --no-sandbox \
  --disable-gpu --user-data-dir=/tmp/chrome-wp --no-pdf-header-footer \
  --print-to-pdf=../workpaper/AI-ASC606-Contract-Review-Workpaper.pdf \
  "file://$PWD/workpaper.html"
python3 genoffice_build.py        # workbook via the GenOffice CLI
python3 make_manifest.py          # evidence hashes
```

The source build used a specific Chrome binary and the GenOffice CLI. The command above is the portable form; if headless Chrome is not on PATH, point the command at the installed binary. `proof_render.py` needs Pillow, so run it with an interpreter that has it.
